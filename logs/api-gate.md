# API-GATE: рішення контрольної точки

**Що оцінюється:** контракт `spec/openapi.yaml` (OpenAPI 3.1, 38 операцій) за
затвердженою `spec/srs.md`, адендум `logs/api-addendum-1.md`, проєктні нотатки
`docs/api-design.md`, сценарії `tests/api/`. Серверної реалізації немає — вона
починається в лаб. №5.

## Чекліст (факти перевірені командами; зведення підготував агент)

| # | Умова | Результат | Доказ |
|---|---|---|---|
| 1 | Кожна суттєва операція має обґрунтований зв'язок з REQ-ID | Так: 38/38 операцій мають `x-req-ids`; усі ID існують у SRS; 49 з 50 REQ-F пов'язані з операціями, REQ-F-022 скасовано (LS-40) | `python tests/api/lint_contract.py` (перевірка `x-req-ids` за SRS); `plan/traceability.md`, колонка «API operation» |
| 2 | Ресурси та термінологія відповідають глосарію | Так: видання, екземпляр, читач, бібліотекар, адміністратор, видача, бронювання, штраф, рекомендація, сповіщення, аудит-лог | `docs/api-design.md`, розд. 2 |
| 3 | URI та HTTP-методи послідовні | Так: іменники в множині, `kebab-case`; `GET` лише читає; `POST` створює або виконує дію; `PATCH` частково змінює; `DELETE`/`PUT` не використовуються | `docs/api-design.md`, розд. 3 |
| 4 | Для операцій визначені request і response schemas | Так: усі операції з тілом мають схему вводу, усі успішні відповіді з тілом — схему виводу; приклади відповідають схемам | `lint_contract.py`: `openapi-spec-validator` і перевірка прикладів за схемами |
| 5 | Визначені коди стану HTTP та єдина модель помилок | Так: 400, 401, 403, 404, 409, 423; усі відповіді помилок посилаються на `Error` | Перевірка в `lint_contract.py`; `docs/api-design.md`, розд. 6 |
| 6 | Передбачені позитивні й негативні сценарії | Так: 35 позитивних, 25 негативних; кожна з 38 операцій має успішний сценарій; 5 BDD-сценаріїв SRS (8.1–8.5) відтворені числами | `tests/api/scenarios.py`; `logs/api-scenarios-report.md` |
| 7 | API не розкриває без необхідності деталі реалізації | Так: паролі `writeOnly`, ідентифікатори — UUID, хеші й журнал системного логування не виставлені; персональні дані — лише для читача-власника та персоналу | Схеми `Reader`, `Account`; `getReader` 403 |
| 8 | Специфікація проходить автоматичну валідацію | Так: `openapi-spec-validator` (стандарт OpenAPI 3.1.0) і правила проєкту | `python tests/api/lint_contract.py` |
| 9 | Mock API запускається на основі специфікації | Так: `tests/api/mock_server.py` стартує з `spec/openapi.yaml`, не має стану й бізнес-логіки | `python tests/api/mock_server.py` |
| 10 | Сценарії відтворюються через mock API | Так: 60/60 сценаріїв; статус, тип вмісту та тіло відповіді перевіряються за схемою контракту; навмисно хибне очікування в сценарії дає FAIL | `python tests/api/run.py` |

## Обмеження та невирішене

* Mock повертає приклади й перевіряє форму запиту, але не виконує бізнес-логіку
  (ролі, стан даних, розрахунок штрафу). Коди 403/404/409/423 у сценаріях вибираються
  заголовком `Prefer: code=…`. Правильність правил перевірятимуть тести лаб. №5.
* Прогалини SRS B1–B5 (`logs/api-addendum-1.md`) не закриті; жодна не блокує
  контракт, але B1 (відмова у видачі боржнику) варто вирішити до тестів видачі.
* `spec/srs.md` усе ще містить REQ-F-022 без позначки про скасування (див.
  адендум, розд. C). Розбіжність некритична для контракту, але її слід усунути.
* Нові коди помилок, ролі та пагінація — технічні уточнення (адендум, розд. A);
  нової функціональності в контракті немає.

Рішення приймає студент; агент підготував лише чекліст і зведення фактів. Якщо
