# Адендум №1 до SRS: уточнення, внесені під час проєктування REST API (лаб. №4)

**Дата:** 22.10.2026 (доповнено A11–A15 і B6 після перевірки контракту)

**Що змінюється:** текст `spec/srs.md` **не змінюється**. Нижче — рішення, які
SRS прямо не містить, але без яких неможливо описати контракт API. Кожне є
уточненням способу доступу до вже затвердженої вимоги, а не новою функціональністю.
Це відповідає кроку 14 лабораторної: нова поведінка оформлюється уточненням чи
адендумом, а не «тихо» додається в OpenAPI.

## A. Технічні уточнення (поведінка вимоги не змінюється)

| № | Уточнення | Вимога | Місце в контракті |
|---|---|---|---|
| A1 | Автентифікація — `POST /auth/login`, у відповідь bearer-токен; усі операції, окрім публічних, вимагають його | REQ-F-009…014, 048 | `bearerAuth`, `login` |
| A2 | Читач задає пароль при реєстрації (форма в BDD 8.4 пароля не називає, але вхід і відновлення пароля його передбачають) | REQ-F-015, 047 | `ReaderRegistration.password` |
| A3 | Початковий пароль акаунта адміністратора чи бібліотекаря задає той, хто його створює | REQ-F-010, 013 | `AccountInput.password` |
| A4 | Підтвердження email і скидання пароля виконуються `POST` з токеном; посилання з листа веде на сторінку веб-застосунку, яка викликає API (зміна стану через `GET` недопустима) | REQ-F-016, 047 | `confirmReaderEmail`, `resetPassword` |
| A5 | Запит на скидання пароля завжди повертає `202`, щоб не розкривати, чи існує акаунт | REQ-F-047, REQ-NF-003 | `requestPasswordReset` |
| A6 | Видалення акаунтів не виставляється: лише деактивація (`active: false`). Критерій REQ-F-011 щодо «видалення» головного адміністратора виконується відсутністю операції, а `PATCH` його акаунта дає `403 protected_account` | REQ-F-011, 012, 014 | `updateAdministrator` |
| A7 | Списки (читачі, видання, видачі, сповіщення тощо) мають пагінацію `page` / `pageSize` | REQ-F-021, 038, 043 | `Page`, `PageSize` |
| A8 | Пошук читача `GET /readers?q=` потрібен бібліотекарю, щоб вибрати читача для видачі | REQ-F-018, 050 | `listReaders` |
| A9 | Звіт «Боржники» містить ПІБ, email і телефон читача; доступний лише персоналу | REQ-F-040, 050 | `DebtorsReport` |
| A10 | Єдина модель помилки та закритий перелік кодів помилок (`docs/api-design.md`, розд. 6); `requestId` зіставляє відповідь із системним журналом | REQ-NF-005 | `Error` |
| A11 | Видачу в стані `compensated` не можна повернути через систему — `409 loan_already_closed`. SRS (BDD 8.5) каже, що подальші дії бібліотекар вирішує поза системою | REQ-F-029 | `returnLoan` |
| A12 | Звіт «Топ видань» має параметр `limit` (1–100, за замовчуванням 10): SRS не задає розмір «топу» | REQ-F-039 | `getTopEditionsReport` |
| A13 | Період звіту, де `from` пізніше за `to`, — `400 validation_failed` | REQ-F-039, 041 | `getTopEditionsReport`, `getLibraryLoadReport` |
| A14 | Некоректний ідентифікатор у шляху (не UUID) — `404 not_found`: такого ресурсу не може існувати | усі операції з `{id}` | відповіді `404` |
| A15 | Окремий код `invalid_token` для недійсного або простроченого токена з листа | REQ-F-016, 047 | `confirmReaderEmail`, `resetPassword` |

## B. Прогалини SRS, які API свідомо не закриває

Це не нова поведінка, а місця, де SRS мовчить. Контракт їх не вигадує; їх потрібно
вирішити до реалізації відповідних тестів (лаб. №5).

| № | Прогалина | Що зроблено в API v1 | Пов'язано з |
|---|---|---|---|
| B1 | SRS не вимагає відмови у видачі читачу з простроченням чи боргом (BDD 8.1 згадує це лише в умові «Given»; відмову передбачає тільки скасоване продовження REQ-F-022) | `createLoan` такої відмови не описує | REQ-F-018, 027 |
| B2 | Не визначено, як бронювання переходить у `fulfilled`. Припущення: система виставляє його, коли бібліотекар оформлює видачу цьому читачу на це видання | Окремого поля чи операції немає | REQ-F-023, 026 |
| B3 | Не визначено, чи може читач сам скасувати бронювання (REQ-F-026 згадує «скасування», REQ-F-025 — лише автоматичне) | Операції скасування немає | REQ-F-025, 026 |
| B4 | Не визначено повторне бронювання одного видання тим самим читачем | Окремого коду помилки немає | REQ-F-023, 024 |
| B5 | Не визначено рольову матрицю дій, окрім явно названих (напр., чи бачить адміністратор каталог екземплярів) | `x-roles` виведено із розділів 2.3 і 6 SRS | REQ-F-046 |
| B6 | REQ-F-023 «резервує екземпляр за читачем», але глосарій не має стану екземпляра «заброньовано» (лише доступний / видано / пошкоджений / списаний) | Стан `Copy` не змінюється; видача такого екземпляра іншому читачу — `409 copy_not_available`. Чи потрібен окремий стан, вирішує SRS | REQ-F-006, 018, 023 |

Якщо рішення за B1–B6 змінять поведінку, спочатку вносяться зміни в SRS (`spec:`),
потім — у контракт.

## C. Вимога, для якої операції немає

REQ-F-022 (самостійне продовження терміну) скасовано рішенням LS-40
(`plan/tickets.md`, `logs/plan-gate.md`). Операції продовження в API немає. Сам
текст REQ-F-022 і критерій у `spec/srs.md` досі не оновлено; це розбіжність
SRS ↔ рішення LS-40, яку слід закрити окремим коміттям `spec:` до лаб. №5.
