## 5. Відомі обмеження та відкриті питання

| # | Що | Вплив на рішення |
|---|---|---|
| 1 | Веб-інтерфейсу немає (лише REST API за умовою лаби); REQ-NF-004 оцінено людиною лише на рівні кроків API | Некритично для лаби |
| 2 | Справжньої пошти немає: листи з токенами пишуться у `var/mail/outbox.jsonl` | Свідоме рішення для локального розгортання |
| 3 | Прострочення, штраф, автоскасування броні й сповіщення не показати на живому сервері без очікування — перевірено тестами з керованим годинником та демо-даними | Некритично |
| 4 | Продуктивність (REQ-NF-001) перевірено в тестовому середовищі, не на цільовому обладнанні | Некритично для MVP |
| 5 | Прогалини SRS, не закриті ні адендумами, ні реалізацією (`logs/api-addendum-1.md`): B3 (ручне скасування броні), B4 (повторне бронювання тим самим читачем), B5 (рольова матриця понад явно названі дії) | Не блокують; кандидати на наступні адендуми |
| 6 | Рекомендації виключають усі видання з будь-якою видачею читача, навіть повернуті давно; валідатор погодився | Прийнято |
| 7 | SQLite у режимі WAL: при раптовому вимкненні живлення можна втратити останні секунди записів | Прийнятно за REQ-NF-002 (щодобове копіювання) |

## 6. Підстави для рішення

* **GO** — критичних невиконаних умов немає: усі вимоги верифіковано, валідація пройдена,
  зміни внесено лише через адендуми з gate, дефекти валідації усунуто.
* **REVISE** — якщо після перегляду потрібні доопрацювання (напр., закрити B3–B5 перед
  здачею або змінити якусь поведінку); виправлення йдуть новими комітами, gate повторюється.
* **STOP** — відмова від результату; для цієї роботи не обґрунтовано.
