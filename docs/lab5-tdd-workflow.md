## Завдання агенту

Реалізувати REST API за `spec/openapi.yaml`, виконуючи етапи `plan/tickets.md`
послідовно (етап 2 → 3 → 4). Для кожної групи вимог:

1. **Test.** Написати тести з SRS (критерії розд. 7, BDD розд. 8) і контракту —
   позитивні, негативні, граничні. Не дивитися на код реалізації; тест не
   підганяється під наявну поведінку.
2. **Red.** Запустити тести й переконатися, що вони падають **з очікуваної
   причини** (немає маршруту, неправильний код чи значення), а не через помилку
   в самому тесті. Закомітити (`test:`).
3. **TEST-GATE.** Підготувати зведення тестів для людини; рішення GO/REVISE
   ухвалює людина (`logs/test-gate-*.md`).
4. **Green.** Після GO написати мінімальний код, що проходить тести. Закомітити
   (`feat:`).
5. **Логи.** Після кожного контрольного запуску переглянути `var/log/library.log`:
   немає несподіваних ERROR, кожен запит має запис із `requestId`.

## Обмеження

* Контракт є обов'язковим зовнішнім інтерфейсом: шляхи, поля, коди й моделі
  помилок не змінюються без зміни специфікації через адендум.
* Прогалини B1–B6 у базовій реалізації закриваються так, як уже вирішив контракт;
  нова поведінка — лише через адендум (крок 4).
* Функціональний код без тесту, написаного раніше, не приймається.
* Рішення Gate і валідацію ухвалює людина (`plan/roles.md`).

## Системний журнал (REQ-NF-005 + вимога лаб. №5)

* Файл `var/log/library.log`, окремо від аудит-логу (REQ-F-049).
* Кожен HTTP-запит — запис INFO: метод, шлях, статус, тривалість, `requestId`.
* Кожна необроблена помилка — рівно один запис ERROR зі стеком.
* Формат: часова мітка, рівень, джерело (модуль), повідомлення, `requestId`.
