# Бібліотечна інформаційна система

REST API бібліотечної системи, розроблений за методологією **Specification Driven Development (SDD)**:  
`специфікація (SRS) → контракт API (OpenAPI 3.1) → розробка через тестування (TDD) → реалізація → верифікація та валідація`.

Навчальний проєкт (лабораторні роботи №1–6).

---

## Швидкий старт

### 1. Вимоги до середовища
* **Python:** `>= 3.12` (розробка та тестування на Python 3.13)
* **Менеджер пакетів:** `pip`

### 2. Встановлення залежностей
```bash
pip install -r requirements.txt
```

### 3. Запуск сервера
```bash
python -m uvicorn library.main:app --app-dir src --port 8000
```

Після запуску:
* **Інтерактивна документація (Swagger UI):** `http://127.0.0.1:8000/docs` (відображає затверджений контракт `spec/openapi.yaml`).
* **OpenAPI специфікація (JSON):** `http://127.0.0.1:8000/openapi.json`.
* **База даних:** файл SQLite `var/library.db` (створюється автоматично в режимі WAL).
* **Головний адміністратор:** створюється автоматично при першому старті:
  * **Email:** `chief@library.local` (налаштовується через `LIBRARY_CHIEF_EMAIL`)
  * **Пароль:** `Chief-Pass-2026` (налаштовується через `LIBRARY_CHIEF_PASSWORD`)
* **Вихідна пошта:** службові листи з токенами підтвердження реєстрації та скидання пароля записуються у файл `var/mail/outbox.jsonl`.
* **Системний журнал:** структурований JSON Lines лог із `requestId` записується у `var/log/library.log`.

### 4. Генерація демо-даних
Для ручної перевірки сценаріїв (з простроченими видачами, штрафами та чергами):
```bash
python tests/seed_demo.py --reset
```

| Дія | Команда | Опис |
|---|---|---|
| **Усі автоматичні тести** | `python -m pytest` | 263 тести pytest (модульні, інтеграційні, нефункціональні) |
| **Валідація контракту** | `python tests/api/lint_contract.py` | Перевірка відповідності стандарту OpenAPI 3.1 та зв'язку з SRS |

| **Оновлення матриці** | `python tests/update_traceability.py` | Перерахунок колонок реалізації та тестів у `plan/traceability.md` |

| **Аналіз стилю коду** | `python -m pyflakes src/library tests` | Перевірка відсутності невикористаних імпортів та синтаксичних помилок |

## Структура репозиторію

| Каталог | Вміст |
|---|---|
| `spec/` | SRS (`srs.md`), контракт OpenAPI (`openapi.yaml`), адендуми змін (`addendum-*.md`) |
| `src/library/` | Реалізація застосунку на базі FastAPI та SQLAlchemy |
| `src/library/routers/` | Ендпоінти REST API за доменами предметної області |
| `tests/app/` | Автоматичні тести застосунку (263 тести на pytest) |
| `tests/api/` | Контрактні тести, валідатор та mock-сервер |
| `plan/` | Тікети, ризики, ролі, розклад та матриця простежуваності |
| `logs/` | Протоколи рішень контрольних точок (Gates), звіти верифікації та валідації |
| `docs/` | Посібник користувача, довідник API, конвенції та стек |
| `var/` | Локальна база даних, журнали та вихідна пошта (ігноруються в git) |

## Процес розробки (SDD + TDD)

Кожна зміна поведінки системи проходить суворий цикл:
1. Фіксація вимоги в специфікації або адендумі (`spec:`)
2. Написання автоматичного тесту, що падає з очікуваної причини (`test:`, стан Red)
3. Рішення контрольної точки Gate (`logs/*gate*.md`, `gate:`)
4. Реалізація мінімально необхідного функціонального коду (`feat:`, стан Green)
5. Рефакторинг без зміни зовнішньої поведінки (`refactor:`)
6. Оновлення документації та матриці простежуваності (`docs:`)
