# Декомпозиція SRS на тікети (затверджено PLAN-GATE, лаб. №3)

Джерело планування: `spec/srs.md` (затверджена версія, SPEC-GATE + адендум №1).
Усі тікети посилаються на ID вимог. Нової функціональності немає: тікет без
вимоги-джерела — це або `Documentation` / інфраструктурний, або вилучається.

Тимчасові ідентифікатори `LS-NN` будуть замінені номерами GitHub Issues.

Типи: Gate, Documentation, Test, Feature, Verification, Validation
(`Specification` та `Addendum` зарезервовані на випадок REVISE, див. розділ 4).

Принцип (SRS 1.4): для кожної групи вимог тікет `Test` блокує тікет `Feature`;
`Gate` блокує реалізацію етапу.

## 4. Відкриті питання для PLAN-GATE

1. REQ-F-022 (прогалина): SRS не визначає тривалість продовження та ліміт.
   Рішення: оформити Addendum (LS-40), який блокує тест LS-15 (рішення PLAN-GATE: GO за цієї умови). Припущення, що
   перевіряється з автором: продовження дає ще один термін за правилом
   REQ-F-019 без ліміту кількості, поки немає черги й боргів; без
   продовження після терміну діє штраф REQ-F-027.
2. REQ-F-025, 029, 035…037 (дії за часом): залишено як є; планувальник
   допустимий, оскільки SRS його не забороняє (заборона REQ-F-027 стосується
   лише перерахунку штрафу).
3. Вибір технологічного стеку (LS-02): залишено як є; SRS 1.3 стек не фіксує.
